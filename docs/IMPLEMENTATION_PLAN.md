# Scam Shield: prioritized delivery plan

Source: SCAM_SHIELD_SDD.pdf v1.0, 18 September 2026, pages 1–15. The repository was empty on inspection. This is a build plan, not evidence of completed acceptance. See DELIVERY.md for actual results.

## Scope and delivery strategy

Build React/JavaScript, Vite, Tailwind, Firebase Auth, Firestore, second-generation callable Functions, Vision OCR and Firebase Hosting configuration. English only; verified accounts; deterministic rules; ephemeral input and results. All three priorities are required for the complete MVP. Priority is execution order, not permission to omit security or launch criteria. Ship one vertical text flow first, then reuse its analysis/report path for OCR. Develop with emulators and mock Vision; never replace the real server with browser verdicts.

Exclude native apps, extensions, social login, billing, LLMs, calibrated probabilities, live URL fetching/reputation, QR decoding, non-image attachments, admin dashboards, scan history, public sharing, automated reporting and multilingual analysis (D-01–D-06, pp. 2, 14). Do not provision or publish production without the release decisions below.

Estimates are engineering planning ranges for one experienced full-stack developer, with part-time QA and product-owner availability. They include tests and review, not cloud approval wait time. Fast implementation can precede independent release acceptance.

## Critical path and efficiency

P1-01 → P1-02/04 → P1-03/05/06 → P2-01/02/03/04 → P3 acceptance. Use one shared schema/source catalog and one report renderer. Introduce accessibility, tests and privacy with each feature; P3 audits them rather than adding them late. Avoid new infrastructure/services beyond the SDD. Stop broadening tests once relevant checks pass; use failures to guide corrections. Document any unmet gate rather than presenting mocks as production validation.

## Design issues resolved or requiring sign-off

1. **Incomplete content:** the SDD names known-incomplete input but omits its API representation. Add an optional `incomplete` boolean, default false, to the strict analysis schema and expose a checkbox. This produces insufficient information. No language detection or hidden inference is added.
2. **Deletion recreation race:** every profile/reservation/commit checks the deletion job transactionally. Keep the job until Auth is removed; require a live Auth lookup before profile creation. Never recreate a missing profile in completion handlers.
3. **Retention wording:** daily cleanup alone cannot guarantee “at most 48 hours” after a 48-hour expiry. Use an hourly cleanup with a 47-hour eligibility cutoff for requests (and 6d23h for quotas), backed by TTL, and document scheduling outages as a release/operations risk. Exact hard-deletion timing cannot be guaranteed during outages.
4. **R07 overlap:** `remote access` is in both conjunction groups; the literal specification permits the same span to satisfy both. Keep that behavior explicit in tests and assess false positives before release.
5. **Benchmarks:** deterministic synthetic fixtures are developer regression data until two reviewers approve labels. Do not claim the SDD quality gate on self-generated examples alone.
6. **Delete unverified account:** page 8 requires verified email on every callable, including deletion. Follow it, show verification instructions before deletion; product may later revise this policy explicitly.
